    Front-end redesign — Stage 1: audit and direction¶

    Status: validated 2026-10-10 (stage 1 of 4). Decisions (§9): direction A with the two borrowings; achromatic chrome; amber narrowed; space and names in the URL; plan diff parsed from the logs until A1; stage-3 dependencies approved; API items A1–A10 stay in this document (no issues opened). Stage 2 output: docs/DESIGN.md v2. No application code is changed by this stage. Scope: front/ only. The API, the invariants of CLAUDE.md §4/§8 and the semantic rules listed in the brief are treated as fixed. Everything that would need API work is collected in §6, with the SPECS section it touches.

    1. Summary¶

    The front works feature by feature but does not yet tell the truth at a glance. The audit found one defect that matters more than all the visual ones: the overview shows each environment's most recent run, not its state, so a production plan waiting for a second approver can read CANCELED on the stack page and the graph (C1). Second, the run page shows the run's state but not the decision: everyone sees the same enabled Confirm whatever their rights, with no reason, no triggerer, no confirmer, and an "applied" run looks the same as a "no changes" one (C2).

    What is wrong, in order of cost to the user:

    1. Truth (C1–C3): misleading env summaries, a decision bar without reasons, a three-number plan while the full diff sits in the logs, a rail that spins on finished runs and greys out failed ones, logs out of chronological order.
    2. Semantics (C4): amber, green and violet each carry several meanings; five state colours fail AA in light theme, queued fails in both, the active nav item fails in dark.
    3. Reach (C5, C6): no responsive layout (the on-call mobile path is unusable), no keyboard, no live regions, users land on an empty space, URLs carry no state, Queue unreachable.
    4. Safety in config (C7): one click disables four-eyes on prod; icon-only and untyped deletes.
    5. Foundations (C8): the DESIGN.md system was never installed: no fonts, no light theme, no Radix, no LogViewer/PlanDiff/RunActionBar/EnvCell, 281 inline styles, lint not configured.

    The API already holds most of what the redesign needs (§6): staleness, confirmer and timings, the text plan, the after_seq log protocol, the destroy, cancel and with_downstream triggers. Ten items need API work for an exact version (A1–A10); each has a today-compatible design.

    Recommendation (§8): Direction A, "Blueprint, finished" — the matrix as home, one page per entity, a fixed decision bar, the rail as signature — with B's personal decision signal ("needs you" vs "waiting on someone", next-decision navigation) and C's cascade preview on demand. Plus a stricter visual language: achromatic chrome, amber reserved to the decision, two outcomes for finished, contrast fixed in both themes, fonts shipped.

    Seven questions for you are in §9.

    2. Method¶

    • Stack. The dev stack ran in this session's container: Postgres and Garage from deploy/docker-compose.dev.yml; API, worker (OpenTofu 1.12.2, runner=local) and Vite run on the host because the container images could not be built behind the session proxy. Same code, same seed, same dev login. The OpenTofu registry is blocked from this sandbox, so the fixtures use only the built-in terraform_data provider.
    • Data. On top of task seed I drove the real API to produce nearly every state the run page can show: unconfirmed on dev, staging (mixed +1 ~1 −1) and prod (four-eyes, triggered by bob); applied; no changes; discarded; canceled; queued behind an active run; mocked (used_mocks=true); failed in tofu (undeclared variable on a feature branch); failed in an after_plan platform hook; destroy awaiting confirmation; dependency cascade; a drift check that found drift; stale envs after task push-change; comments. Not produced: a running apply (transient), a run group (no with_downstream UI to trigger it, and nothing exposes groups, A5).
    • Screenshots. Playwright (chromium), 1440 × 900 and 390 × 844, full page, for admin, and for alice and bob where rights differ (prod four-eyes run, mocked run, audit, notifications). 28 views × 2 widths × 2 themes = 112 images in screenshots/before/, named <nn>-<view>--<width>-<theme>.png. The light theme cannot be selected in the UI (C8): those images set data-theme="light" on <html> from the harness.
    • Code. Read all of front/src (pages, components, api/*, stories, tests), the e2e smoke test and the relevant API routers/schemas to check what data exists. Contrast ratios computed with the WCAG 2.x formula from the token values in front/src/styles/tokens.css.
    • Checks at baseline. pnpm typecheck passes; pnpm test passes (4 files, 19 tests); pnpm lint fails (no ESLint config/dependency).

    3. What fails today, by cause¶

    Grouped by root cause rather than by screen. Each cause lists its symptoms with the screenshot that shows them (before/<name>--<width>-<theme>.png). Fixing a cause fixes every symptom under it.

    C1. The front shows the latest run, not the state of the environment¶

    Every place that summarises an environment (stack page, graph node) shows runs.list(env)[0]: the most recently created run, whatever its type. Three different things are mixed into one badge: tracked runs, proposed (PR) runs and drift-check runs.

    • demo-network/prod reads CANCELED while an unconfirmed prod plan waits for a second pair of eyes. A queued run was created and cancelled after it, so it became "latest" and hid the pending decision (04-stack-network--1440-dark, 30-graph--1440-dark).
    • demo-app/prod reads QUEUED while a mocked plan blocks it (30-graph).
    • demo-app/dev reads FAILED: the failure is a proposed run on a broken feature branch; the environment itself was applied successfully (30-graph).
    • demo-app/staging reads FINISHED: that is the drift check, which found drift (drift_status=drifted). The DRIFT chip exists on the stack page but not on the graph.
    • Staleness (stale=true on network/dev and network/staging) appears nowhere.

    This is the single most dangerous defect for the 3 a.m. user: the overview can say "nothing to do" while a production decision is pending. An env summary needs to be composed: the active run (if any, which is unique per env, SPECS §3.5) first, else the last tracked outcome, with drift, staleness, lock and mocks as separate modifiers. Proposed and drift runs never stand for the env.

    C2. The run page shows state, not the decision¶

    The run page answers "what state is it in" and leaves "can I act, and should I" to guesswork.

    • Confirm looks identical for everyone. Bob (writer, who triggered the prod run, cannot confirm on two counts) sees the same enabled amber Confirm as an admin (12-…-bob vs 11-…-admin). He learns the rule from a 403 after clicking. Alice on the mocked run gets an enabled Confirm and a 409 (17-run-mocked). No reason is ever shown, though everything needed is in the run, the env, the tier catalog and /auth/me (§6).
    • The four-eyes status is invisible. Neither the triggerer nor the confirmer is displayed; trigger_user_id/confirmed_by_user_id are never rendered. "Who may still confirm" is unknowable.
    • Disabled actions on terminal runs. A failed or finished run still shows Confirm (amber at 50 % opacity, which reads as a brown enabled button) and Discard (19-run-failed-hook, 15-run-finished-nochanges). Cancel is never offered, although the API supports it on queued/unconfirmed.
    • "Finished" is ambiguous (gap 4). The no-change run (15) and the applied run (14) look the same: green FINISHED, rail "Apply ✓". The no-change run never applied anything.
    • The rail lies in two cases. On a finished run the last segment shows a blue spinner ("active": ORDER.finished === at, RunPage.tsx:46), so a finished run looks like it is still working (15). On a failed run every segment turns grey with a ▷ icon (19): it reads as "not started", and where it failed is only in an error line that says after_plan.
    • The plan is three numbers. +1 ~1 −1 with no resource names, while the full resource diff is sitting in the logs a few hundred lines below (10-run-unconfirmed-staging-mixed). The destroy confirmation says "3 resource(s) will be destroyed" without naming them (20-run-destroy). +4 ~0 −0 colours the zeros too, so a reader scans three coloured numbers for one fact.
    • "No plan yet" on a run whose plan ran and was rejected by a check (19).
    • No staleness banner although network/staging is stale with an unconfirmed plan on it (10).
    • No time anywhere. No created/finished timestamps, no durations, no relative age.

    C3. Logs are a dump, and partly out of order¶

    • The API sorts chunks by (phase, seq); phase is a string, so checking sorts before planning: the after_plan hook output appears above the plan it checked (19-run-failed-hook). The front concatenates without re-ordering. (The API ordering is a bug to report; the viewer must order by time — line t — regardless.)
    • The phase/section name is prefixed on every line (planning planning planning…), eating 9–30 characters of a 12 px mono line; blank tofu lines become "planning" alone.
    • 400 px tall box inside a long page: the log is the thing an on-call reader wants most and it gets the least room. No line numbers, anchors, search, follow-tail, full screen, sections, or jump to the first error. Every line is a React node (no virtualization).
    • Every WebSocket signal re-downloads the whole log (and the run and the comments), although the signal carries phase and max_seq and the endpoint accepts after_seq.

    C4. The colour system has drifted from "one hue, one meaning"¶

    Measured contrast (WCAG 2.x) of the current tokens, text on its real background:

    Token Dark on base / surface / raised Light on base / surface / raised Verdict
    state-queued 4.39 / 4.02 / 3.50 4.09 / 4.31 / 3.83 fails AA both themes (used for 12 px badge text: QUEUED, DISCARDED, CANCELED)
    accent (violet) 4.96 / 4.54 / 3.96 6.01 / 6.34 / 5.64 fails on raised in dark = the active nav item
    state-running 5.92 / 5.41 / 4.72 4.39 / 4.63 / 4.12 fails in light
    state-unconfirmed = decision 9.10 / 8.32 / 7.26 3.64 / 3.84 / 3.41 fails in light — DESIGN §3.1 claims AA
    state-finished 7.45 / 6.82 / 5.95 3.05 / 3.22 / 2.86 fails in light
    state-failed 5.65 / 5.17 / 4.51 5.07 / 5.36 / 4.76 passes (barely on raised)
    mock 6.57 / 6.01 / 5.24 4.58 / 4.84 / 4.30 fails on raised in light
    border (inputs) 1.52 / 1.39 / 1.21 1.34 / 1.41 / 1.25 fails 3:1 non-text contrast for form controls

    Disabled controls use opacity: 0.5, which halves all of the above.

    Hue collisions:

    • Amber means "needs a human" (DESIGN §3.1) but also paints the drift chip (SPECS §19.5 says neutral), the plan ~, the "open thread" counter and FALLBACK. In 04-stack-network, an amber UNCONFIRMED and an amber DRIFT read as the same urgency.
    • Green means finished, but also "HTTP 2xx" and "online" on the workers page (41-workers), and the plan's +.
    • Violet (brand) fills primary buttons ("Plan", "New stack", "Create pool"), links, the active nav, the notification badge and log event names (41-workers). It sits between running-blue and mocked-magenta; the brand is the loudest colour on most screens, louder than state.
    • Magenta on the graph marks every edge that has a mock defined (has_mock), not edges that served a mock: in the demo every edge is dashed magenta (30-graph), so the "not real" signal is saturated and means nothing.
    • Telemetry noise: the workers page counts 46 "Warnings+errors", nearly all of them the worker's 25 s long-poll jobs/claim flagged (slow), which is its normal behaviour (41-workers).

    C5. No responsive layout, no keyboard, no live regions¶

    • At 390 px the side nav keeps its 208 px, the topbar overflows to ~840 px, and the run page is clipped mid-word with the Confirm card off-screen (11-…-admin--390-dark). The on-call mobile journey (DESIGN §7: read a run, confirm or discard) is unusable.
    • No skip link, no shortcuts, no aria-live region (state changes are silent for screen readers), no visible focus style on most controls, the walkthrough dialog has no focus trap, the notification popover is not a Radix popover (no Escape, no focus return).
    • The graph's React Flow controls and edge labels keep the library's white default skin in dark theme (30-graph), and nodes have no accessible name.

    C6. Orientation: space, URL and navigation¶

    • The home opens on an empty space. The space list is ordered by name and the first one wins: admin, alice and bob land on default — "No stacks yet" — while all the demo data is in demo (02-stacks-default-space). The switcher is a small select in the topbar.
    • The space is in-memory: a reload, a new tab or a shared link always reopens default. The breadcrumb's first segment shows the selected space, not the entity's (10: "default / demo-network / …" for a stack that lives in demo).
    • Stack URLs are UUIDs and the breadcrumb prints them raw (default / stacks / 01a12765-e228-…, 04).
    • /queue is not reachable from the UI. Audit is in everyone's nav but admin-only: bob gets an empty table with no message (51-audit-bob).
    • An environment has no page and no run history: from the UI you reach only its latest run (C1). Older runs are reachable only from a notification or a pasted URL.
    • Notifications say "Run failed" / "Run finished" without naming the stack or environment (only approval requests carry the env), with locale timestamps (62-notifications).

    C7. Configuration surfaces: friction where none is needed, none where it is¶

    • A single click on the four-eyes checkbox of the prod tier saves immediately: the strongest safety switch in the product has less friction than renaming a stack (61-settings). Same for a user's allowed tiers and role.
    • Icon-only destructive actions (DESIGN §9 forbids them): tier delete is a red × (61-settings), config items use a bare trash icon; pool delete, variable-set delete, hook delete and state force-unlock are one click without typing the name, and force-unlock is offered to non-admins (the API refuses them afterwards).
    • The environment card folds ten tabs (Inputs, Dependencies, Hooks, Notifications, Cloud, State, Command, Promote, Settings, Danger) behind "Configure" (05-stack-network-configure): daily actions (Promote, Command, the run history that does not exist) sit next to rare configuration.
    • The destroy run type, with_downstream and Cancel exist in the API with no UI (§6).

    C8. The design system exists on paper only¶

    • Fonts are not shipped (system fonts render, 03). Light theme unreachable without devtools: every *-light.png was produced by setting data-theme="light" from the test harness.
    • No primitives library; 281 inline style= attributes; ui.tsx re-implements Button, Tabs, Checkbox, Card with inline colour objects. The same table markup (header row, cell padding, border) is re-written in nine files.
    • Pages mix data fetching, layout and behaviour: StackDetailPage.tsx 654 lines, GraphPage.tsx 394, HealthPage.tsx 381, RunPage.tsx 338. Per-env queries poll every 4 s on the stack page and every 30 s per graph node, on top of WS invalidation.
    • pnpm lint does not run (no ESLint dependency or config).

    6. What the API gives us, and what it does not¶

    The redesign is front-only, so I checked what each idea can stand on. Three findings matter more than the rest.

    a. More is available than the front uses. These exist in the API today and the front ignores them:

    Data / endpoint Where Use in the redesign
    RunOut.confirmed_at, claimed_at, commit_author, worker_id, command api/app/runs/schemas.py (missing from front/src/api/types.ts) "Applied" vs "No changes" (finished + confirmed_at), who/when on the action bar, worker on the run page
    trigger_user_id, confirmed_by_user_id + GET /users/mentionable (open to all) already typed, never rendered Four-eyes status: "triggered by bob · confirmer must be someone else"
    Environment.stale, commits_ahead, affects_project_root, head_sha, locked, drift_run_id typed, never rendered ↑N chip (attenuated when affects_project_root=false), stale-plan banner, lock indicator, link to the drift run
    POST /environments/{id}/runs {type: "destroy"} runs.trigger accepts it, no caller A destroy trigger (with can_destroy gating and the typed-name friction)
    POST /environments/{id}/runs {with_downstream: true} not in the client "Plan with downstream" (starts a run group, SPECS §9.4)
    POST /runs/{id}/cancel in the client, no caller Cancel a queued / unconfirmed run (409 while a worker executes it, SPECS §4.1)
    GET /runs/{id}/logs?phase=&after_seq= the client always fetches everything Incremental log streaming: the WS signal carries {kind, run_id, phase, max_seq} (SPECS §5.3), so the viewer can fetch only the new chunks instead of the whole log
    Log line timestamps lines[].t rendered nowhere Per-phase durations on the rail (first/last line per phase), timestamps toggle
    Plan text in the logs: phase="planning", section="plan" = tofu show -no-color of the saved plan (worker/agent/main.py) shown raw A parsed, grouped PlanDiff (see b.)
    GET /graph edges with policy rendered as a table Cascade preview before Confirm: BFS over edges from the env (§8)

    b. The structured plan is not served, but the text plan is. GET /runs/{id}/plan returns only {plan_summary, used_mocks} (api/app/runs/router.py:169); the masked plan.json artifact is reachable only from the worker API. The human-readable plan is in the logs, one resource block per # <address> will be created | updated in-place | destroyed | must be replaced, with + ~ - -/+ attribute lines. A front-side parser of that format gives everything the brief asks for on the Plan tab (destroys and replaces first, tag-only changes detected by attribute name, search, counts) with today's data. It is a text format, so it is a stopgap: the parser must fall back to the raw log block on anything it does not recognise, and never drop a line (a destroy is never hidden).

    c. Permissions are evaluated on instance defaults only. GET /auth/me returns the user's instance role/allowed_tiers/can_destroy; the effective values are per space (SPECS §2.4, Phase F) and GET /spaces/{id}/members is space-admin only. So a front-computed reason ("tier prod not in your allowed tiers") can be wrong for a user whose membership differs from their defaults. The redesign computes the reason client-side for display, labels it as such when it cannot be sure, and always surfaces the API's own 403 detail verbatim when an action is refused.

    API defects found along the way¶

    Not design work, but they affect what the front can show; reported here rather than fixed (this is a front-only redesign):

    • GET /runs/{id}/logs orders by (phase, seq) with phase a string, so checking chunks come before planning ones (api/app/runs/router.py:165). The viewer will order by line time regardless.
    • Environment.commits_ahead is never computed (only cleared, api/app/environments/router.py:334), so the ↑N chip can only be the binary "behind" variant SPECS §9.6 allows as a fallback (A6).
    • A run that fails at an after_plan check reports error = "after_plan" (the stage name) and no plan_summary, although the plan ran.
    • GET /queue reports apply_affinity_hold for every confirmed run, also after the affinity window has passed (api/app/workers/pools_router.py:146); no_compatible_worker is never produced. Found in stage 4.
    • A failed command run is audited as run.apply_failed. Found in stage 4.

    7. Three directions¶

    Three directions that differ in what the product puts first, not only in looks. All three keep the fixed rules (no browser storage, tokens only, WS invalidates, typed-name friction, destroys never collapsed, sensitive never revealable, colour never alone, amber = needs a human, mocked = magenta modifier) and all three ship the same identity components. The wireframes use the seeded demo data.

    Legend for the wireframes: ▰ done segment, ▱ pending, ◐ running, ⏸ waiting on a human, ✕ failed, ✓ finished with changes applied, = finished with no changes, ◆ mocked modifier, ↑3 branch 3 commits ahead (a bare ↑ until A6), ≈ drift.

    Direction A — "Blueprint, finished"¶

    Idea. Build DESIGN.md as written, then fix what it gets wrong: the matrix is home, every entity has its own page, the decision bar is a fixed band, the phase rail is the signature.

    Navigation. Labelled side nav (Overview, Graph, Queue, Workers, Audit, Variable sets, Settings), labels always visible as DESIGN §4 decided; below 1024 px it becomes a drawer, below 768 px a bottom bar with the four on-call destinations. Breadcrumb in the top bar built from entities, not the path. ⌘K for jumping and acting. New routes: / (matrix), /s/:space/stacks/:stack, /s/:space/stacks/:stack/envs/:env (env page with run history), /runs/:id?tab=plan&line=planning:87. The space goes into the URL.

    Matrix ("All environments" scope). Same matrix as A, rendered inside the list pane; selecting a cell opens the env in the detail pane instead of navigating.

    Idea. The matrix is the dependency graph: stacks are rows, environments are columns, and the edges between cells are drawn on the matrix, labelled with the outputs they carry. A run opens as a side sheet over the map; selecting a cell lights its downstream cascade.

    Navigation. Top bar only (no side nav): Map · Queue · Audit · Settings, plus ⌘K. The map is home.

    Visual language — independent of the direction¶

    These apply whichever direction you pick; each is a departure from DESIGN.md, justified against the audience. They are proposals, see §9.

    1. Achromatic chrome; violet becomes brand-and-focus only. Today violet fills the primary buttons, the active nav item and every link. Violet sits between running-blue (#4C8DFF) and mocked-magenta (#EC6AB4); under deuteranopia and tritanopia the three collapse towards each other, and at a glance a violet "New stack" button reads like a state. If every chromatic pixel in the chrome means a state, the matrix scans by colour alone in a second (with the label and icon still there for meaning). Primary buttons become high-contrast neutral (text-primary on bg), links are underlined text, violet stays on the logo, the focus ring and the selection.
    2. Amber narrowed to exactly one meaning. Drift goes neutral with ≈ (as SPECS §19.5 already says); the plan's ~ update goes neutral-bright with the glyph (an update is the least alarming action, it should not look like the decision colour); open threads and FALLBACK keep amber only if they block or demand the decision (FALLBACK does, per §15.5; open threads do not → neutral).
    3. Two outcomes of finished. ✓ APPLIED +a ~c −d (finished with confirmed_at) and = NO CHANGES (finished, zero summary) get different glyphs and labels; "planned" for proposed runs. Same green hue, distinct shape and text. Fixes gap 4 everywhere a run is shown.
    4. "Needs you" versus "needs someone". Same amber, different label and weight: a solid amber badge when the current user can act, an outlined one when the run waits on someone else, with the reason. This is the reserved human signal made personal.
    5. Diff tokens separate from state tokens (--color-diff-create, -destroy, -update, -replace) even where the hue is shared, so a future change to one does not silently change the other; destroy and replace always carry −/± and a text label.
    6. Contrast fixed, both themes: every state colour ≥ 4.5:1 on the background it is actually drawn on (badge text is 11–12 px), non-text UI (input borders, focus ring) ≥ 3:1. Light theme reachable (follows the OS, in-memory override).
    7. Ship the fonts. IBM Plex Sans + JetBrains Mono self-hosted (the identity of "data is mono" currently relies on whatever monospace the OS has).
    8. Type scale kept dense (13 px UI, 12 px data, 11 px eyebrow only), titles reduced to 16/20 — page titles at 20 px currently eat the first row of every page for a word that the breadcrumb already says.

    8. Recommendation¶

    Direction A as the skeleton, with one idea taken from B and one from C, plus the visual-language changes listed above.

    Why A: the brief makes the matrix the strongest screen and the home, which rules B out as the skeleton; C puts it first too, but its signature (edges routed across a table) is custom canvas work that degrades with every added dependency and pushes the accessible equivalent into a second-class list, and its sheet-over-map run page is the wrong container for a production destroy review. A gives every entity a page with a stable URL, which is what an incident channel needs, and it is the model SPECS, PLAN and the e2e scenario already use, so the migration risk sits in the visuals, not in the information architecture.

    What A borrows:

    • From B, the personal decision signal and the triage loop. The attention zone says needs you (solid amber, you can act) versus waiting on someone (outlined, with who and why), and the run page has "next decision" (] / [) so a reviewer walks through pending decisions without going back home. This is gap 3 (approval clarity) without B's three-pane layout.
    • From C, cascade visibility on demand. Not drawn permanently: on the run page, the decision bar lists the downstream environments the apply can trigger (BFS over GET /graph edges: always → "will plan", on_output_change → "plans if change", never → omitted); on the matrix, selecting a cell outlines its downstream cells and names the outputs that flow. This is gap 5 with today's data.

    How it answers the brief's five gaps: (1) matrix home with attention zone, lag, drift and mocked signals per cell; (2) plan review with destroys and replaces first, tag-only changes collapsed but counted, search; (3) decision bar that names the rule, the triggerer, the current user's standing and what is still missing; (4) ✓ APPLIED versus = NO CHANGES; (5) cascade preview before Confirm.

    Consequences to plan for in stages 3–4: new routes (the old /stacks/:id and /runs/:id keep working as redirects so shared links do not break), the Playwright happy path gains the matrix and the run page, and an env page appears (today an environment has no page and no run history: only its latest run is reachable).
